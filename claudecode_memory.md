# SEVEN7 AUDIT — Mémoire de session (claudecode_memory.md)

Outil d'audit externe automatisé, référentiel **SYSCOHADA révisé / OHADA**, en production avec de vrais cabinets clients. Déployé sur Firebase Hosting (`app.seven7.ci` / `seven7-audit.web.app`, projet Firebase `seven7-audit`).

## 1. ARCHITECTURE ET FRAMEWORK

- **JavaScript vanille pur**, aucun framework (pas de React/Vue/Node backend). Portée globale (`var`/`function` au top-level), pas de modules ES dans l'app elle-même.
- **Structure des fichiers sources** :
  - `src/js/` — fichiers numérotés (`01-noyau.js` → `51-rapprochement-bancaire.js`), chacun une responsabilité. L'ordre des fichiers dans `build/manifeste.json` fait foi pour l'ordre de concaténation dans le HTML final — **mais tout est concaténé en UN SEUL bloc `<script>`** : les fonctions déclarées (`function nom(){}`) sont donc hoistées et accessibles partout quel que soit l'ordre du manifeste (vérifié empiriquement : `51-rapprochement-bancaire.js` est listé AVANT `45-securite-import.js` dans `manifeste.json` alors que le premier appelle des fonctions du second — ça fonctionne quand même grâce au hoisting, tant qu'aucun code de PORTÉE GLOBALE, hors fonction, ne dépend d'un `var` pas encore assigné).
  - `src/app.html` — le template HTML unique de l'application (markers `/* @@NOM@@ */` substitués au build).
  - `src/vitrine/` — le site public **seven7.ci**, cible Firebase Hosting séparée (`vitrine`).
  - `build/build.mjs` — concatène `src/app.html` + `src/js/` en `dist/seven7-app_v2_9_NAV-ECLATEE.html`.
  - `build/version.mjs` — écrit `src/js/00-version.js` (bandeau version). **Toujours commiter le code AVANT de lancer `estampiller`**, sinon le hash affiché porte `+modifié` (un `.claude/launch.json` non suivi, par exemple, suffit à déclencher ce flag — le supprimer ou le committer avant d'estampiller). Séquence propre : commit code → `pnpm run estampiller` → `pnpm run build` → commit du stamp seul (convention du projet : petit commit dédié « Estampille vX · hash »).
  - **Substitution `.env`** : marqueurs `@@ENV_FIREBASE_*@@`, jamais versionnés.
- **Firebase** : Firestore et Auth appelés directement côté client, pas de backend Node. Règles testées via émulateur — **sans JDK installé, ces tests sont skip** (91 tests systématiquement skippés, normal).
- **Gestionnaire de paquets : `pnpm`** (pas `npm` — préférence explicite de l'utilisateur, confirmée le 26/08). Les scripts (`pnpm run build`, `pnpm test`, `pnpm run estampiller`) sont identiques à `npm run X` (mêmes commandes dans `package.json`).
- **Tests** : `tests/*.test.js`, Node `--test` natif. `pnpm test` lance tout. Deux styles de harnais (`tests/harness.js`) :
  - `chargerApplication()` + `vm` sandboxé — pour les fonctions PURES (parsing, matching, calcul), rapide (<50ms/test).
  - `JSDOM` (`runScripts:'dangerously'`) — pour les tests DOM/UI, ~1-6s par test (charge tout le bundle 1,7 Mo). **Toujours `d.window.close()` en fin de test**, sinon un timer réel (session-inactivité 30 min) peut faire tourner le processus en tâche de fond.
  - Suite complète (26/08, fin de session) : **370/370 tests passent**, 91 skip (émulateur).
- **Déploiement** : `npx firebase deploy --only hosting:app`. **Toujours confirmer avec l'utilisateur avant chaque déploiement**, sans exception — production réelle. `Cache-Control: no-cache` sur l'app.
  - ⚠️ **PWA installée (desktop)** : après un déploiement, une app PWA déjà installée peut continuer à tourner sur l'ANCIEN service worker jusqu'à fermeture complète + réouverture (le cycle de vie standard des service workers ne bascule pas sur les onglets déjà ouverts). Un cas réel (26/08) a nécessité une désinstallation/réinstallation complète pour voir la nouvelle version — informer l'utilisateur de fermer complètement l'app (pas juste l'onglet) ou de faire Ctrl+Maj+R après chaque déploiement s'il rapporte un comportement qui persiste malgré un correctif déployé.
- **Rollback** : `npx firebase hosting:rollback --site seven7-audit` — **bloqué par le classificateur auto mode de Claude Code** (permission requise), l'utilisateur doit soit confirmer explicitement dans le chat pour relancer, soit l'exécuter lui-même dans un terminal.

### CORRIGÉ (26/08 puis 30/08) — TROIS bugs de production sur l'import du Grand Livre
Le cabinet a signalé un blocage total (« la page ne répond plus ») à l'import d'un gros Grand Livre (5 000 à 7 000 lignes chez lui). Trois causes distinctes, indépendantes : les deux premières corrigées le 26/08, la 3e le 30/08 après que le cabinet a re-signalé le blocage.

1. **`requestAnimationFrame` en arrière-plan** (`04-grand-livre.js`, `importGLLinesChunked`) — l'enchaînement des lots d'import (300 lignes/lot) dépendait de `requestAnimationFrame`, qui se met en pause dès que l'onglet n'est plus au premier plan (changement de fenêtre pendant un gros collage). L'import restait bloqué indéfiniment après le premier lot. **Reproduit et confirmé identique sur la version qui tournait AVANT toute intervention de cette session (51d2f0c)** : bug préexistant, pas une régression de cette session. Corrigé en enchaînant par `setTimeout` seul. Testé en conditions réelles (navigateur, pas seulement JSDOM) : import de 7 000 lignes réussi en ~12s, et 8 imports concurrents de 5 000 lignes chacun (simulation multi-utilisateurs sur une seule machine, pire cas que la réalité) tous aboutis sans blocage dur. Commit `50a1f82`.
2. **Course avec l'auto-sauvegarde** — le clic qui lance l'import (bouton « Coller les écritures ») est lui-même un clic DANS l'onglet, qui déclenche via un listener global (`10-config-collaboration.js`) une sauvegarde automatique ~1,3s après. Pour un import de plusieurs milliers de lignes (plusieurs dizaines de secondes même corrigé), la sauvegarde se déclenchait EN PLEINE CROISSANCE du tableau, les deux se disputant le même thread. **C'est ce second bug qui expliquait la persistance du blocage sur le poste du cabinet malgré le premier correctif et une réinstallation complète de l'app** (PWA — voir note §1 sur le cycle de vie du service worker, qui a aussi ajouté de la confusion sur le moment exact où le correctif est devenu visible). Corrigé avec `pauseAutosave` (même principe qu'`applyingRemote`, déjà existant), exposé via `window.SEVEN7_PAUSE_AUTOSAVE`/`window.SEVEN7_SCHEDULE_SAVE` : l'import suspend l'auto-sauvegarde de son onglet, puis déclenche lui-même une sauvegarde immédiate et complète une fois tous les lots posés. Filet de sécurité : si l'import échoue en cours de route, la pause est explicitement levée (jamais de sauvegarde bloquée en silence). Commit `4a3b93b`.
3. **Balayage global du formatage des montants** (`28-format-montants.js`) — ce module installe un `MutationObserver` sur `document.body` (`subtree:true`). Pendant l'import par lots, chaque `table.appendChild(fragment)` le réveille ; sa callback relance `formaterTousLesMontants(document)` qui **rescanne TOUT le document** (`querySelectorAll` sur des dizaines de milliers de champs, conversion `type=number`→`text` + reformatage de chacun). Coût O(n²) purement synchrone → écran figé, MALGRÉ les correctifs #1 et #2. C'est ce qui restait quand le cabinet a re-signalé le blocage le 30/08. Corrigé : `importGLLinesChunked` suspend ce balayage via `window.SEVEN7_PAUSE_FORMAT_MONTANTS(true)` pour la durée de l'import, puis relance UN seul passage ciblé sur son tableau (`formaterTousLesMontants(table)`) à la fin — et en cas d'échec (`annulerImport`). Vérifié en navigateur réel : 7 000 lignes importées en ~9 s, thread réactif en continu (probe setInterval 50  ms tournant sans accroc), contre un blocage quasi total (~16 ticks sur 19 s) en simulation pré-correctif. Commit `097f93c`, estampille `<ESTAMPILLE_30_08>`, déployé le 30/08.
- **Point ouvert non confirmé** : le correctif #3 a été déployé mais **pas encore reconfirmé par le cabinet sur son poste**. S'il signale ENCORE un blocage à l'import : les trois causes connues sont corrigées, chercher une 4e — pistes jamais isolément testées en conditions réelles Firestore (pas de compte de test) : `freezeDynamicValues` + capture `innerHTML` sur un très gros tableau au moment de la sauvegarde finale ; le `recomputeGLTable` final (querySelectorAll par ligne × 7 000) ; `computeControleGLSondage` appelé en fin de `recomputeGLTable`.

## 3. CHOIX TECHNIQUES ET RÈGLES MÉTIER LOGÉES

- **Mapping SYSCOHADA** : `PARAM_SPEC` (`25-moteur-etape2.js`), inchangé.
- **Sens comptable relevé/banque** (documenté dans `51-rapprochement-bancaire.js`, s'applique partout où c'est pertinent) : sur le relevé, crédit = encaissement, débit = décaissement (convention bancaire usuelle) ; en comptabilité, le compte banque est un compte d'ACTIF — un encaissement l'augmente à son DÉBIT, un décaissement le diminue à son CRÉDIT. L'inverse du relevé.
- **Format de collage Grand Livre** (`04-grand-livre.js`, `pasteGLTable`) : tabulations, ordre `compte / intitulé / date / référence / libellé / débit / crédit`. Réutilisé par le rapprochement bancaire pour reporter les écritures manquantes.
- **Import par lots** (`importGLLinesChunked`) : lots de 300 lignes, enchaînés par `setTimeout` (pas `requestAnimationFrame`, voir §2), auto-sauvegarde suspendue pendant toute la durée.
- **`parseFloat` interdit hors de `parseNum`** — règle testée (`tests/parsenum.test.js`, régression réelle passée). `parseNum` gère déjà les formats français (virgule/point décimal, séparateurs de milliers) ; toute nouvelle conversion numérique doit passer par lui, y compris pour des nombres qui ne sont pas des montants (ex. numéro de série Excel dans `rbParserDate`).
- **Gotchas techniques à retenir** :
  - Un `MutationObserver` avec `childList:true` (sans `subtree`) sur un conteneur ne réagit QUE si un enfant DIRECT du conteneur est ajouté/retiré — pas aux mutations plus profondes (ex. lignes ajoutées à une `<table>` elle-même enfant du conteneur observé). Motif utilisé à plusieurs endroits (`glObserverIntegrite`, `rbObserverSync`) : vérifier la profondeur réelle de l'élément muté avant de soupçonner une boucle.
  - Tout clic DANS un onglet suivi (`document.addEventListener('click', ...)` global, `10-config-collaboration.js`) programme une sauvegarde ~1,3s après — y compris les clics sur des boutons qui lancent un traitement long. Si un futur traitement long est ajouté (import, calcul), vérifier s'il faut suspendre l'auto-sauvegarde le temps du traitement (`window.SEVEN7_PAUSE_AUTOSAVE`).
  - `freezeDynamicValues` (avant capture `innerHTML` pour sauvegarde) : pour `<textarea>`, fait `el.textContent = el.value` — donc un `<textarea hidden>` utilisé comme stockage d'état JSON (comme `rb-releve-json`) survit correctement à la sauvegarde/restauration sans mécanisme dédié.
  - `grandLivreData` (getter, `02-balances-modele.js`) est une vue FUSIONNÉE en lecture seule de `grandLivreBilanData`/`grandLivreGestionData` — recalculée à chaque accès (nouveau tableau `.concat()`), jamais assignable directement.
  - Environnement de test sans backend Firebase (JSDOM ou navigateur local statique) : `db`/`dossierId` sont `undefined`, donc `scheduleSave` retourne toujours tôt — impossible de tester la VRAIE écriture Firestore en local sans le projet de test `seven7-audit-test` (nécessite JDK pour l'émulateur, absent de cet environnement).
